# zzzync push-protocol hardening audit

Date: 2026-06-22
Workflow: zzzync-hardening-audit, 42 agents (6 finders, dedup, 2 verifiers per finding, report). 22 raw findings, 17 unique, all confirmed, 0 disputed, 0 refuted.

## Summary

The zzzync push-protocol library is in good security shape for its threat model. The authorization and authentication core is sound and confirmed correct: `allow` is mandatory default-deny with both gates running before any CAR import (`allow-default-deny-confirmed`), the IPNS record is cryptographically bound to the dialer's proven key with no key-substitution bypass (`record-bound-to-proven-key-confirmed`), value codec/hash gating is tight (`parsedrecordvalue-gating-confirmed`), and the non-CAR pre-allocation read paths (varint, IPNS key, IPNS record) are correctly bounded before allocation (`preallocation-bounds-confirmed-sound`).

All 16 findings are confirmed (both verifiers agree); none are disputed. Severity counts (confirmed):

- Critical: 0
- High: 1 (CAR pre-allocation memory DoS)
- Medium: 2 (no total stream deadline / slow-loris; dialer ack false-failure race)
- Low: 6
- Info: 7 (4 are positive confirmations that specific defenses hold)

Bottom line: one genuine high-severity DoS (`car-unbounded-preallocation-dos`) should block v6.0.0 until fixed; the two medium issues (slow-loris deadline, dialer ack race) are strongly recommended for the release. No integrity, authentication, or authorization bypass exists.

## Confirmed findings

### High

#### CAR block/header sizes are buffered fully before any cap rejects them (memory DoS)
- ID: `car-unbounded-preallocation-dos`
- Location: `src/handler.ts:183-247` (inner reader generator 185-193; post-yield checks at 214/218/221; root check 198). Root cause in `@ipld/car` `decoder.js` (`chunkReader.read`, `readBlock`, `readHeader`).
- Issue: `readCarFile` feeds the raw untrusted stream straight into `CarBlockIterator.fromIterable` via the inner generator at `handler.ts:185-193`, which drains `bs.read()` with no byte budget. The size caps (`bytes.byteLength > MAX_BLOCK_BYTES` at 214, running `byteLength > maxByteLength` at 218, `++blockCount > maxBlockCount` at 221) all run inside the `for await` loop, i.e. AFTER `@ipld/car` has fully materialized the block/header. `@ipld/car` decodes each section length as an effectively unbounded varint (up to ~2^56) then calls `reader.exactly(length)`, accumulating chunks into one contiguous `new Uint8Array(sum)` with no upper bound. The same applies to the CAR header (read before `getRoots()`/the root-equality check at 198) and to a block CID's multihash length. The `byteStream` 4MiB overflow guard never fires because the generator continuously drains into the decoder's separate buffer; the idle timer bounds time, not peak memory.
- Impact: Memory-exhaustion / OOM DoS. A dialer that clears the challenge and allow gates can force a single contiguous allocation of nearly arbitrary size (per block, per header, or per CID multihash) before any of MAX_BLOCK_BYTES (2MiB), DEFAULT_MAX_CAR_BYTES (5MiB), or DEFAULT_MAX_BLOCK_COUNT (10000) apply. With `maxInboundStreams` defaulting to 5 (`handler.ts:459`) and no per-peer/global connection cap, the peak multiplies (e.g. ~1GiB transient at 200MiB x 5 streams). The advertised 2MiB/5MiB bounds give a false sense of safety. Verified empirically: a 200MiB declared block drove `arrayBuffers` 0->201MiB and `rss` 62->263MiB at the moment of yield; a 200MiB declared header buffered ~202MiB before the dag-cbor decode failed.
- Fix: Bound the bytes handed to `@ipld/car` BEFORE the decoder buffers them. In the inner generator (`handler.ts:185-193`) track cumulative bytes pulled from `bs.read()` and throw once the running total (framing included) exceeds `maxByteLength`, starving a malicious declared length at EOF. Additionally cap any single section by checking `sectionLength - cidLen > MAX_BLOCK_BYTES` against the declared varint before `exactly()` allocates, and bound the header by reading only a small `MAX_CAR_HEADER_BYTES` prefix. Add a regression test asserting peak `process.memoryUsage().arrayBuffers` (NOT `heapUsed`) stays bounded for a huge declared block and header. Note: the scratch probe `test/dos-probe.test.ts` showing `peakHeapDelta=0.9MiB` is a false negative; it samples `heapUsed`, which excludes off-heap ArrayBuffer backing stores.
- Verifier confidence: real, avg 0.90 (0.88 / 0.92); both confirm code accuracy and `high` severity.

### Medium

#### No cumulative/wall-clock deadline; permits indefinite slow-loris
- ID: `no-total-stream-deadline-slowloris`
- Location: `src/utils.ts:201-222` (idle timer; `onMessage = resetIdle` at 211); used by `createZzzyncHandler` `src/handler.ts:390-393` (`DEFAULT_IDLE_TIMEOUT_MS=10s`).
- Issue: The only time bound on a handler stream is `streamSignal`'s idle timer, reset on every incoming `message` event. There is no cumulative/wall-clock deadline over the whole stream or the CAR-receive phase. A dialer that sends one byte slightly more often than `idleTimeoutMs` keeps the stream alive indefinitely at near-zero cost. `deadlineSignal`/`withDeadline` exist in `utils.ts` but are never wired into the handler. Confirmed empirically (a read under a 120ms idle window survived 489ms by trickling one byte every 60ms) and documented as a deliberate tradeoff in the CAR-reader-hardening spec ("Timeouts (DEFERRED)").
- Impact: Cheap, long-lived stream occupation. With `maxInboundStreams=5` (`handler.ts:459`) and no per-peer cap, a handful of trickling streams from one peer can pin all inbound `/zzzync/push/1.0.0` slots, denying service to legitimate dialers. Total data is still bounded by the CAR caps, but a slot can be held effectively unbounded in time. Requires passing the allow-list/handshake gate first, which raises attacker cost on private allow-lists.
- Fix: Add a hard total deadline for the stream (or at least the CAR-receive phase) alongside the idle timer, combining `streamSignal` with `deadlineSignal(signal, maxStreamMs)`; make it configurable (optionally disabled by default) via `CreateHandlerOptions`. `CreateHandlerOptions` already exposes `idleTimeoutMs?`, so adding `maxStreamMs?` and merging via `anySignal` is a small change.
- Verifier confidence: real, avg 0.925 (0.93 / 0.92); both `medium`, code accurate.

#### Dialer falsely reports failure on ack timeout (missed one-shot `remoteCloseWrite`)
- ID: `dialer-ack-missed-remoteclosewrite-false-failure`
- Location: `awaitHandlerClose` `src/dialer.ts:171-180` via `eventPromise` (`utils.ts:84-113`); reached from `zzzync` at `dialer.ts:224-236`.
- Issue: After writing the CAR, the dialer calls `await stream.close()` (224) then `awaitHandlerClose` (226), which waits up to `ackTimeoutMs` for the handler's `remoteCloseWrite` via `eventPromise`. `eventPromise` guards only the already-aborted signal case (`utils.ts:106-109`); it never checks the stream's already-closed state. `remoteCloseWrite` is a one-shot, non-replayed event (`AbstractMessageStream.onRemoteCloseWrite` sets `remoteWriteStatus='closed'` and dispatches exactly once). The listener is attached only AFTER `await stream.close(...)`, so if the handler already half-closed by then (it reads the CAR, runs `onReceive`, closes its write side, which can propagate during/just after the dialer's own close over a real transport), the event is already gone. Reproduced: with `remoteCloseWrite` fired before attach, `awaitHandlerClose` rejected only after the full timeout (402ms for a 400ms ack).
- Impact: False negative on the dialer: a fully successful push (handler pinned and served the content) is reported as a thrown error after stalling for the full `ackTimeoutMs` (default 15s, `constants.ts`). A retry loop re-pushes already-stored content (at-least-once wart), and callers cannot distinguish "handler never closed" from "handler closed before I looked." Not a security hole; trusted-dialer reliability/correctness only. Trigger probability is transport/timing dependent (the in-process mock muxer often delivers after attach, hiding it).
- Fix: Short-circuit when the remote write side is already closed before attaching, mirroring the `signal.aborted` guard: in `awaitHandlerClose`/`eventPromise` check `if (stream.remoteWriteStatus === 'closed' || stream.status === 'closed' || 'reset' || 'aborted') return;` (or pass an `alreadySettled` predicate into `eventPromise`, checked after the signal guard). `remoteWriteStatus` is on the public `@libp2p/interface` `Stream` type, so no internals are touched. Separately, treat an ack timeout as best-effort (resolve with `ack: false` rather than throwing) so a delayed close does not provoke duplicate re-pushes.
- Verifier confidence: real, avg 0.915 (0.93 / 0.90); both `medium`, code accurate.

### Low

#### `maxByteLength` undercounts CAR framing/header/CID bytes
- ID: `car-maxbytelength-undercounts-framing`
- Location: `src/handler.ts:217-220` (`byteLength += bytes.byteLength; if (byteLength > maxByteLength) throw`).
- Issue: The running `byteLength` accumulates only decoded block payload (`bytes.byteLength`). It excludes the CARv1 header, per-section length varints, each section's embedded CID (~36+ bytes/block), and any trailing CARv2 index. Confirmed empirically: a CAR whose total on-wire size exceeds the cap still passes when `maxByteLength` equals the single block's payload size.
- Impact: Resource-accounting gap. With `DEFAULT_MAX_BLOCK_COUNT=10000`, framing overhead (~45 bytes/block, ~450KB) plus an unbounded header is uncounted on top of the 5MiB payload cap, so the real on-wire ceiling is ~5.5MiB plus header. Bounded in practice by block count and the 4MiB byteStream guard, hence low.
- Fix: Account for total bytes consumed from the stream (sum of `bs.read()` lengths in the inner generator) against `maxByteLength`. This is the same mechanism that fixes `car-unbounded-preallocation-dos` and closes the undercount in one change.
- Verifier confidence: real, avg 0.88 (0.88 / 0.88); both `low`, code accurate.

#### Default `maxInboundStreams` of 5; no per-peer/global cap
- ID: `max-inbound-streams-saturation`
- Location: `registerZzzyncHandler` `src/handler.ts:453-466` (`maxInboundStreams: 5` at 459).
- Issue: libp2p enforces `maxInboundStreams` per protocol; once 5 inbound `/zzzync/push/1.0.0` streams are concurrently open, new ones are reset. There is no per-remote-peer cap and (per the hardening design's stated non-goal) no global cross-connection limit. 5 is very small to fully occupy.
- Impact: Low effort to saturate inbound capacity. Whether it becomes durable depends mainly on the missing total deadline (`no-total-stream-deadline-slowloris`); with that fixed, a one-off oversized push only briefly holds a slot. The 10s idle timeout cycles fully-silent connections, so durable saturation requires the slow-loris trickle path. Self-rated as an amplifier of the two findings above, not an independent exploit.
- Fix: Keep the value small but document pairing it with the total-stream deadline; consider a modest default bump and recommend (or implement at the consuming-app layer) a per-remote-peer limit. Ensure the slow-loris fix lands so occupying a slot is time-bounded.
- Verifier confidence: real, avg 0.76 (0.70 / 0.82); both `low`, code accurate. (Lower confidence reflects its framing as a secondary/amplifier observation, not the code accuracy.)

#### `verifyChallenge` accepts non-canonical (high-S) secp256k1 encodings on the wire
- ID: `verifychallenge-high-s-defense-in-depth`
- Location: `verifyChallenge` `src/challenge.ts:41-48` (secp256k1 branch); interacts with `@libp2p/crypto` `hashAndVerify` calling noble `secp.verify(... lowS default true)`.
- Issue: For secp256k1, `verifyChallenge` does `secp.Signature.fromBytes(sig, 'compact').toBytes('der')` (`challenge.ts:44`) and passes DER to `publicKey.verify()`. noble's `fromBytes('compact')` accepts a high-S (malleable) signature and re-encodes it to valid DER, but `@libp2p/crypto`'s verify inherits noble's default `lowS:true`, which rejects high-S. End-to-end a malleated high-S variant returns `false`, so this is NOT an acceptance bypass today, and the dialer always emits canonical low-S sigs.
- Impact: None today. Latent: malleability rejection is an undocumented transitive property of `@libp2p/crypto` passing `lowS:true`; if that default flips or the dep is swapped, `verifyChallenge` would silently start accepting two valid signatures per challenge. Even then, the challenge binds handler peerId + dialer key + both nonces and the response is consumed once, so there is no useful exploit (signature non-uniqueness only).
- Fix: Make the guard explicit and dependency-independent: after `fromBytes('compact')`, reject if parsed `s` is not low-S (`s > n/2`) before converting to DER, or pass `lowS:true` explicitly. Add a test that a high-S variant of a valid response is rejected.
- Verifier confidence: real, avg 0.935 (0.90 / 0.97); both `low`, code accurate.

#### Dialer `stream.close()` flush/drain has no zzzync-level deadline
- ID: `dialer-close-drain-no-deadline`
- Location: `zzzync` `src/dialer.ts:224` (`await stream.close({ signal: options.signal })`).
- Issue: Every other dialer step is wrapped in `withDeadline` with `writeTimeoutMs`, but the final `stream.close()` after the CAR uses only the optional caller signal. `AbstractStream.close` awaits `pEvent(this,'idle'/'drain',{signal})` when there is unsent/undrained data; with `options.signal` undefined (the documented common case for the local dialer), a handler that stops reading right as the last CAR chunk is buffered leaves `close()` parked on `drain` with no zzzync-level timeout, unblocking only via the transport `inactivityTimeout` (~120s) or a configured write-buffer overflow abort. A handler that closes/errors instead rejects via `rejectionEvents:['close']`; only the silent-stop-reading handler triggers this. The dialer-timeouts design explicitly aimed to cover "even a no-signal caller," yet `close()` escaped the treatment.
- Impact: A malicious or wedged handler going silent at upload's end can stall the dialer's `close()` for up to the transport `inactivityTimeout` per push instead of `writeTimeoutMs` (default 5s), tying up the dialer and muxer stream. Bounded (not infinite), hence low. One verifier notes the exact trigger is narrow (last CAR data fits the yamux window but TCP stalls on the final frame) and the practical bound may be the connection manager / TCP keepalive rather than a fixed 120s.
- Fix: Wrap the close in the same per-step deadline, e.g. `await withDeadline((deadline) => stream.close({ signal: deadline }), 'closed write', 'failed while closing write', deadlineOptions)`, reusing `writeTimeoutMs`.
- Verifier confidence: real, avg 0.86 (0.90 / 0.82); both `low`, code accurate.

#### Handler `onReceive` await is unbounded after `remoteCloseWrite`
- ID: `handler-onreceive-unbounded-await`
- Location: `createZzzyncHandler` `handler.ts:431` (`await onReceive(...)`); idle timer cleared in `streamSignal` `onRemoteCloseWrite` (`utils.ts:212-217`).
- Issue: The handler passes the `streamSignal` signal into `onReceive`, but `readCarFile` reaches EOF only after the dialer half-closes, which fires `remoteCloseWrite`; `onRemoteCloseWrite` clears the idle timer (`utils.ts:212-217`). From then the signal aborts only via `onClose` when `event.error != null` (`utils.ts:195-199`). So a hung/slow `onReceive` at `handler.ts:431` has no zzzync time bound; the passed signal gives a false sense of timeout protection during this phase. `onReceive` is documented to return promptly (`handler.ts:300-311`), so this is contract reliance, not an attacker primitive.
- Impact: A buggy/slow `onReceive` (e.g. a pin or DHT publish that does not return promptly) holds the stream open and consumes one of the limited inbound slots (`maxInboundStreams=5`, `handler.ts:459`) indefinitely; five such stuck streams block further legitimate pushes from that peer. Not attacker-triggerable (app code), hence low.
- Fix: Either document explicitly that `onReceive` is NOT covered by any zzzync deadline once the upload completes, or give it its own bound via `withDeadline`/`deadlineSignal` with a configurable `onReceiveTimeoutMs`.
- Verifier confidence: real, avg 0.92 (0.92 / 0.92); both `low`, code accurate.

#### `readVarint` 10-byte cap and comment are misleading dead code
- ID: `readvarint-10-byte-cap-misleading`
- Location: `readVarint` `src/handler.ts:68-86` (cap `if (varintBytes.length === 10) break;` at 80); decoder `uint8-varint@2.0.4`.
- Issue: `readVarint` collects continuation bytes up to a 10-byte cap with the comment "max varint size is 10 bytes," then calls `varint.decode`. But bundled `uint8-varint@2.0.4` `decodeUint8Array` reads only offsets 0-7 and throws `RangeError` if byte[7] still has the MSB set, so any varint needing 9-10 bytes throws rather than decoding. The `RangeError` is caught by `readIpnsMultihash`/`readIpnsRecord` and rethrown, and lengths are independently bounded by `MAX_IPNS_KEY_BYTES`/`MAX_IPNS_RECORD_SIZE`. So the cap is effectively dead (decode tops out at 8 bytes) and the comment is wrong for this decoder.
- Impact: No exploitable impact today (overlong varints rejected via `RangeError`; length fields independently bounded). Latent maintenance hazard: if `uint8-varint` is swapped for a 10-byte/u64 decoder, the 9-10 byte path would silently open and the "reject overlong" assumption would change. (One verifier rated this `info` rather than `low`; the difference is purely the severity label of a no-impact maintenance hazard, not a code disagreement.)
- Fix: Either cap the loop at 8 bytes to match the decoder and fix the comment, or decode incrementally (append each byte, try `varint.decode`, treat `RangeError` as "need more bytes") with an explicit byte cap, making the overlong rejection explicit rather than incidental.
- Verifier confidence: real, avg 0.935 (0.95 / 0.92); code accurate. Severity: one `low`, one `info`.

### Info

#### `create()` codec-decodes attacker bytes before verifying the hash (bounded; no integrity impact)
- ID: `car-create-decodes-before-hash-verify`
- Location: `readCarFile` `src/handler.ts:232` (`await create({ bytes, cid, codec, hasher })`), calling multiformats `block.js` `create()`.
- Issue: multiformats `create` runs `codec.decode(bytes)` BEFORE `hasher.digest(bytes)` and the CID-equality check, so every delivered block is dag-pb/dag-cbor-decoded before its hash is confirmed. Bytes are size-capped (`MAX_BLOCK_BYTES` at `handler.ts:214`, fully so once `car-unbounded-preallocation-dos` is fixed) and the decoders are not exponential, so decode work is bounded.
- Impact: Minor bounded CPU on unverified-but-size-capped bytes. No integrity impact: a wrong-hash block throws in `create()` before `yield block` (`handler.ts:246`), and each block's CID must already be in `wanted` (seeded from the validated root). 
- Fix: None required. Optionally verify `sha256(bytes) === cid.multihash` before `create()` for strict hash-before-decode ordering.
- Verifier confidence: real, avg 0.97 (0.97 / 0.97); both `info`, code accurate.

#### v0-rooted CARs and identity/non-sha256 links rejected (fail-closed interop edge)
- ID: `car-v0-root-and-identity-cid-interop`
- Location: `readCarFile` `src/handler.ts:198` (`!root.equals(expectedRoot)`) and `230-231` (`getCodec`/`getHasher`); `utils.ts:57-64` (`getHasher`).
- Issue: Two safe-but-restrictive fail-closed edges. (1) `root.equals(expectedRoot)` is version-sensitive and `expectedRoot` is a v1 UnixFs CID, so a CAR legitimately declaring a CIDv0 root (same dag-pb/sha256 digest) is rejected with `ERR_UNEXPECTED_ROOT`. (2) A block whose links include an identity/inline CID or any non-sha256 hash can never be satisfied: such links join `wanted` but fail `getHasher` (sha256-only) / are never delivered, so the DAG reports incomplete. v0 links are handled correctly because `cidKey` normalizes via `toV1` (`handler.ts:171`).
- Impact: Correctness/interop only; fails closed, so no unsafe acceptance. One verifier notes the finding's "confirmed by test" claim for the v0-root case overstates coverage (no v0-specific test in `car.test.ts`) and that `expectedRoot` is v1 only by the dialer's own consistent use of `parsedRecordValue`, not by type guarantee; the identity-CID rejection fires at the `wanted.size > 0` completeness check rather than precisely at the cited `getHasher` line. These nuances do not change the fail-closed conclusion.
- Fix: If broader compatibility is wanted, compare roots on canonical key (`cidKey(root) === cidKey(expectedRoot)`) and decide explicitly on identity/inline CID support; otherwise document the v1-root/sha256-only/no-inline restrictions as intentional.
- Verifier confidence: real, avg 0.835 (0.85 / 0.82); both `info`, code accurate.

#### Allow-list membership oracle
- ID: `allowlist-membership-oracle`
- Location: `authenticateDialer` `src/handler.ts:338-353` (`allow.multihash` at 338, nonce write at 349).
- Issue: `allow.multihash(dialerPublicKey)` is evaluated BEFORE the handler nonce is generated/written. A disallowed key aborts with no nonce; an allowed key receives a 32-byte nonce. An unauthenticated dialer can probe whether an arbitrary (unowned) public key is allow-listed by observing whether it gets a 32-byte reply before abort. This ordering is also the correct DoS posture (no nonce/signature work spent on disallowed keys), so it is a deliberate tradeoff. It does not enable authenticating as a key you do not own (proof-of-possession and key-bound record validation still apply).
- Impact: Low-value information disclosure; irrelevant for an open allow function, leaks authorized keys for a private allow-list (and only for keys the attacker can already name).
- Fix: If membership must be confidential, issue the nonce first and run `allow.multihash` after the challenge response (or use a constant-shape exchange), accepting extra crypto per probe; otherwise document the oracle as acceptable.
- Verifier confidence: real, avg 0.925 (0.95 / 0.90); both `info`, code accurate.

#### `readByte` relies on `Uint8ArrayList` iterator yielding internal chunks
- ID: `readbyte-uint8arraylist-iterator-fragile`
- Location: `readByte` `src/handler.ts:58-66` (`const [byte] = await bs.read(...); return byte![0]!`).
- Issue: `bs.read({bytes:1})` returns a `Uint8ArrayList`, not a `Uint8Array`. The `const [byte] = ...` destructure uses `Uint8ArrayList[Symbol.iterator]`, which yields internal `Uint8Array` chunks, so `byte` is the first chunk and `byte[0]` its first byte. Correct only because a 1-byte sublist is backed by exactly one single-byte chunk. The double non-null assertion (`byte![0]!`) suppresses that `byte` is a `Uint8Array` and that correctness depends on undocumented internal layout.
- Impact: No current bug. Fragile: a future N>1-byte reuse of this pattern would silently read only the first chunk rather than throwing.
- Fix: Read explicitly via the documented accessor: `const list = await bs.read({ bytes: 1, signal: options.signal }); return list.get(0);`, dropping both non-null assertions.
- Verifier confidence: real, avg 0.90 (0.88 / 0.92); both `info`, code accurate.

#### Pre-allocation bounds for varint/IPNS key/IPNS record are sound (positive confirmation)
- ID: `preallocation-bounds-confirmed-sound`
- Location: `readVarint` `handler.ts:68-86`; `readIpnsMultihash` 88-113 (length check 101); `readIpnsRecord` 135-163 (recordLength check 143); `readChallengeResponse` 123-133.
- Confirmed sound: `readVarint` breaks at 10 bytes (and the decoder throws past 8); `readIpnsMultihash` checks `length > MAX_IPNS_KEY_BYTES` (64) before reading; `readIpnsRecord` checks `recordLength > MAX_IPNS_RECORD_SIZE` (10KiB) before reading and validating; `readChallengeResponse` reads a fixed 96 bytes; handler writes/`importer.import` run under `streamSignal`; the 4MiB byteStream/transport read-buffer guards are in place. The only memory path escaping a pre-allocation bound is the CAR block/header (`car-unbounded-preallocation-dos`).
- Verifier confidence: real, avg 0.97 (0.97 / 0.97); both `info`, code accurate.

#### Record is correctly bound to the dialer's proven IPNS key (positive confirmation)
- ID: `record-bound-to-proven-key-confirmed`
- Location: `readIpnsRecord` (`handler.ts:135-163`, called at 409) + `authenticateDialer` (319-378).
- Confirmed sound: `authenticateDialer` recovers `dialerPublicKey` from the identity multihash `name` (327) and proves ownership via a signature over a challenge including `dialerIpns.bytes` (357-364; `challenge.ts:51-64`). `readIpnsRecord` validates against the SAME `name` via `ipnsValidator(multihashToIPNSRoutingKey(name), ...)` (151-154); `ipnsValidator` enforces routing-key equality against the record's embedded/derived key and verifies signatureV2. No key-substitution bypass: proving ownership of key A and pushing a record bound to key B is rejected.
- Verifier confidence: real, avg 0.98 (0.98 / 0.98); both `info`, code accurate.

#### `allow` is mandatory default-deny; both gates run before CAR import (positive confirmation)
- ID: `allow-default-deny-confirmed`
- Location: `createZzzyncHandler` (380-446); `allow.multihash` (338); `allow.record` (411); ordering (400-429).
- Confirmed sound: `allow` is a required positional param with no library allow-all (only in tests). Both gates are hard throws. Order: `readIpnsMultihash` -> `allow.multihash` (before any nonce/challenge) -> `authenticateDialer` -> `readIpnsRecord` (signature-validated + key-bound) -> `allow.record` -> `parsedRecordValue` -> `readCarFile`. The attacker-controlled CAR is read only after both gates pass, and `allow.record` sees an already-signature-verified, key-bound record.
- Verifier confidence: real, avg 0.98 (0.98 / 0.98); both `info`, code accurate.

#### `parsedRecordValue` codec/hash gating is tight (positive confirmation)
- ID: `parsedrecordvalue-gating-confirmed`
- Location: `parsedRecordValue` (`utils.ts:25-40`); enforced via `handler.ts:420-427` and root check `handler.ts:198`.
- Confirmed sound: value must start `/ipfs/`, parse as a CID, pass `getHasher` (sha256-only), and use dag-pb/raw/dag-cbor; anything else returns null and the handler aborts. The CAR root must equal this exact CID (`handler.ts:198`), and blocks are keyed by canonical v1 CID so codec is preserved. `parsedRecordValue` runs after `allow.record`, which is benign because the value is the real, signature-bound value.
- Verifier confidence: real, avg 0.975 (0.98 / 0.97); both `info`, code accurate.
